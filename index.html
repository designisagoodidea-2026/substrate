Substrate — a reference architecture

An agentic operating system for design organizations.

Most design teams don't need more tools. They need a system that remembers what they learn, improves itself as they work, and maintains its own moving parts — so the people are free to set direction and taste.

01The shift

Designers stop being the hands for the machine.

Today, most of the work of using AI is upkeep — writing context files, curating prompts, wiring up tools, remembering which version is the good one. That work scales badly, and it tends to land on the people you least want spending their time on it. Substrate is built around a single shift: people set intent, taste, and policy; the system handles the upkeep.

01 / memory

Knowledge stops evaporating.

Every project compiles into the organization's memory instead of disappearing when the session ends. The next person — or the next agent — starts from what the last one learned.

02 / teams

The org chart includes agents.

Teams form around the work instead of being assembled by hand. A request finds the right specialists, and those specialists hand off to each other.

03 / capability

Capability is retrieved, not memorized.

You describe what you're trying to do. The system assembles the smallest set of context, skills, agents, and tools that does it — and takes it apart when the work is done.

02The model — seven layers, one idea

A memory graph sits at the center. Five kinds of asset live inside it as versioned nodes. A control plane of agents does the work that used to be done by hand. Two planes — governance and evaluation — touch every layer. Scroll to bring each one in.

L0 · the core

Memory graph

was: a wall of text in one file  →  is: a queryable graph

The single source. Every asset is a node, every relationship an edge, and provenance and freshness are recorded on each one. This is what turns five separate tools into one system — because now they can see each other, and the system can see its own history.

L1 · the nodes

Asset plane

was: static configs  →  is: versioned nodes

Context, skills, agents, playbooks, and tools — each a versioned node instead of a config you write once. Five different kinds of memory wearing the same shape: what's true, how to do things, who does them, how the work runs, and what's permitted.

L2 · identity

Registry & identity

was: a skill someone copied  →  is: a skill you can verify

Every node gets a name, an immutable version, an owner, and a signature. The difference between "a skill someone pasted from somewhere" and a skill with a version, an owner, and a record you can check before you trust it.

L3 · the mediating agents

Control plane

was: you, dispatching by hand  →  is: agents that run the system

The agents that do what people used to do by hand — find the right asset for a stated intent, form the team, mount tools on demand, and keep the graph in good repair. This is the part that makes the system run itself rather than wait for instructions.

L4 · cross-cutting

Governance

was: a discipline you remember  →  is: policy the system enforces

Policy written as rules the system applies on its own. Least privilege by default. Nothing enters without passing a check, and the rules travel with each asset and fail closed when something is unclear. It sits here because the market verifies who published a thing, not whether it's safe to run.

L5 · cross-cutting

Evaluation

was: "this seems better"  →  is: a number that gates the change

Every asset carries a definition of done. "Is this version better?" becomes a measurement rather than an opinion — and a new version ships only when it beats the one it replaces. This is what makes versioning mean something.

L6 · where work runs

Execution

was: output, then forgotten  →  is: output that teaches the system

Where the work actually happens. Its job in the architecture is to report back: what got used, what failed, what diverged from the plan. That record flows into memory, and the system is a little sharper on the next run.

03Buy, assemble, build

The market handed us the edges. The core is ours to build.

Over the past year the connection points standardized and consolidated — the protocols for agent-to-tool and agent-to-agent, the auth model, the formats for skills and registries, now gathered under a single foundation. What did not standardize is the part that matters most: trust, memory, and the loop that improves the system. That line is the difference between what you can buy and what you have to build.

gap 01 — the one that matters most

Trust and safety review

Every registry verifies who published an asset, not whether it's safe to run. The supply chain is already being attacked — typosquatted skills, poisoned tool descriptions, real exfiltration in the wild. Admission control isn't polish. It's load-bearing.

gap 02

Versioning and signing for skills

Real version control exists inside one vendor's API and almost nowhere else. No lockfile, no signing standard. You build the discipline: pin versions, keep a changelog, gate promotion on evaluation.

gap 03

Memory that interoperates

Good memory products exist, with incompatible models — vector, temporal graph, tiered. Build against a pluggable adapter, not a standard that doesn't exist yet, so you can swap the store without rebuilding around it.

gap 04

A trusted directory of agents

You can discover an agent through a published card at a known address. You cannot yet trust a curated registry of them the way you can for tools. For a small team this is a future seam, not a blocker.

gap 05

Evaluation across the whole system

You can grade a skill, a tool, or a memory store on its own. Grading the assembled system end to end is still open ground. For now, evaluate per asset and keep a human review at the seam.

04Building it — phase by phase

You don't build seven layers to get value. You build the spine and stub the rest. Each phase stands on its own and earns the next.

  1. 00 lay the substrate
  2. 01 assets as a registry
  3. 02 stand up the control plane
  4. 03 close the first gap
  5. 04 make "good" a number
  6. 05 close the loop
phase 00

Lay the substrate

One memory store behind a thin adapter. The choice of store matters less than the seam in front of it.

done when: your assets are nodes you can query, and the store underneath can be swapped without rework.
phase 01

Assets as a registry

Skills and plugins in a versioned repository — tags for versions, owners on record, a manifest for discovery. Crude, but real, and close to how the ecosystem already distributes today.

done when: any asset can be found, versioned, and traced to an owner.
phase 02

Stand up the control plane

An orchestrator to route work, and one scheduled maintenance agent that watches for drift and proposes what to update. This is the highest-leverage thing you build yourself — the piece that moves the system from static to self-maintaining.

done when: a maintenance pass runs on its own and proposes real changes.
phase 03

Close the first gap

A written policy and an admission checklist — scan it, read it for injection, sign off — before anything new joins the system. Manual at first. It closes the gap that matters most, and you can automate it later.

done when: nothing enters the system without passing the gate.
phase 04

Make "good" a number

Put evaluations on your most-used assets so a new version has to earn its place instead of being trusted on sight.

done when: a version ships only after it beats the one it replaces.
phase 05

Close the loop

Capture what each run learned as something the maintenance agent reads on the next one. At this point the system stops being a thing you maintain and starts being a thing that maintains itself.

done when: outcomes from one run measurably improve the next.
05 — the through-line

From a setup you configure to a system you cultivate.

The five things a person sets up by hand become versioned nodes in a memory graph — maintained by agents, graded by evaluation, governed by policy. The operator's job moves up a level: from building the workspace to defining the taste and the rules that let the workspace build and improve itself. That is also the move from using these tools to designing the system other people work inside.
