Substrate · a reference architecture

An agentic operating system for design organizations.

Design teams don't just need more tools. They need a system that remembers what they learn, gets better as they work, and looks after its own moving parts, so the people are free to set direction and taste.

scroll to begin ↓
01The shift

Designers stop being the hands for the machine.

A growing share of the work around AI tools is upkeep: writing context files, curating prompts, wiring things together, remembering which version is the good one. It's easy to underestimate, and it lands on the people you least want spending their time on it. Substrate is built around one shift: people set intent, taste, and policy; the system does the upkeep.

01 / memory

Knowledge stops evaporating.

Every project compiles into the organization's memory instead of disappearing when the session ends. The next person to pick it up, or the next agent, starts from what the last one learned.

02 / teams

The org chart includes agents.

Teams form around the work instead of being assembled by hand. A request finds the right specialists, and those specialists hand off to each other.

03 / capability

Capability is retrieved on demand.

You describe what you're trying to do. The system assembles the smallest set of context, skills, agents, and tools that does it, then takes it apart when the work is done.

02The model · five layers, two planes

A memory graph sits at the center. Five kinds of asset live inside it as versioned nodes, from the memory itself up to the place work runs. Two planes, governance and evaluation, cut across all of them. Scroll to bring each one in.

L0 · the core

Memory graph

was: a wall of text in one file  →  is: a queryable graph

The single source. Every asset is a node, every relationship an edge, with provenance and freshness recorded on each one. That is what turns five separate tools into one system. They can finally see each other, and the system can see its own history.

L1 · the nodes

Asset plane

was: static configs  →  is: versioned nodes

Context, skills, agents, playbooks, and tools. Each becomes a versioned node instead of a config you write once. Five different kinds of memory in the same shape: what's true, how to do things, who does them, how the work runs, and what's permitted.

L2 · identity

Registry & identity

was: a skill someone copied  →  is: a skill you can verify

Every node gets a name, an immutable version, an owner, and a signature. That is the difference between a skill someone pasted from somewhere and a skill with a version, an owner, and a record you can check before you trust it.

L3 · the mediating agents

Control plane

was: you, dispatching by hand  →  is: agents that run the system

These agents do what people used to do by hand: find the right asset for a stated intent, form the team, mount tools on demand, keep the graph in good repair. This is the part that lets the system run itself instead of waiting for instructions.

L4 · where work runs

Execution

was: output, then forgotten  →  is: output that teaches the system

Where the work actually happens. Its job in the architecture is to report back: what got used, what failed, what diverged from the plan. That record flows into memory, and the system is a little sharper on the next run.

cross-cutting plane

Governance

was: a discipline you remember  →  is: policy the system enforces

Policy written as rules the system applies on its own. Least privilege by default. Nothing enters without passing a check, and the rules travel with each asset and fail closed when something is unclear. It cuts across every layer because the market verifies who published a thing, not whether it's safe to run.

cross-cutting plane

Evaluation

was: "this seems better"  →  is: a number that gates the change

Every asset carries a definition of done. Whether a new version is better becomes a measurement instead of an opinion. It ships only when it beats the one it replaces. That is what makes versioning mean something across the whole stack.

03Buy, assemble, build

The market handed us the edges. The core is ours to build.

Over the past year the connection points standardized and consolidated. The protocols for agent-to-tool and agent-to-agent, the auth model, the formats for skills and registries are now gathered under a single foundation. What did not standardize is the part that matters most: trust, memory, and the loop that improves the system. Scroll to see which layers you can adopt, which you wire together, and which you build.

the map

Three kinds of layer

Five layers and two planes. Each one is either something you adopt as it is, something you wire together from emerging parts, or something you build yourself. Keep scrolling and the stack sorts itself into those three.

tier 01 · buy

Adopt what exists

Execution runtimes and the asset format (SKILL.md plus plugins) are mature. Take them as they are and spend your effort elsewhere.

tier 02 · assemble

Wire together what's emerging

The registry and the control plane exist only in pieces. The standards are real but young, so you connect them yourself rather than buy them whole.

tier 03 · build

Own the core

The memory graph and the governance plane have no off-the-shelf answer. This is the part you build, and the part worth building, because it is where the system's real value sits.

gap 01 · governance

Trust and safety review

Every registry verifies who published an asset, not whether it's safe to run. The supply chain is already under attack: typosquatted skills, poisoned tool descriptions, real exfiltration in the wild. That makes admission control load-bearing.

gap 02 · registry & identity

Versioning and signing for skills

Real version control exists inside one vendor's API and almost nowhere else. There's no lockfile and no signing standard. You build the discipline: pin versions, keep a changelog, gate promotion on evaluation.

gap 03 · memory graph

Memory that interoperates

Good memory products exist, but their models don't agree: vector, temporal graph, tiered. Build against a pluggable adapter rather than a standard that doesn't exist yet, so you can swap the store without rebuilding around it.

gap 04 · control plane

A trusted directory of agents

You can discover an agent through a published card at a known address. You cannot yet trust a curated directory of them the way you can for tools. For a small team this is a future seam, not a blocker.

gap 05 · evaluation

Evaluation across the system

You can grade a skill, a tool, or a memory store on its own. Grading the assembled system end to end is still open ground. For now, evaluate per asset and keep a human review at the seam.

04Building it · phase by phase

You don't build five layers and two planes to get value. You build the spine and stub the rest. Each phase works on its own and earns the next. Scroll to walk them.

phase 00

Lay the substrate

One memory store behind a thin adapter. The choice of store matters less than the seam in front of it.

done when: your assets are nodes you can query, and the store underneath can be swapped without rework.
phase 01

Assets as a registry

Skills and plugins in a versioned repository: tags for versions, owners on record, a manifest for discovery. Crude, but real, and close to how distribution already works today.

done when: any asset can be found, versioned, and traced to an owner.
phase 02

Build the control plane

An orchestrator to route work, and one scheduled maintenance agent that watches for drift and proposes what to update. This is the piece most worth building yourself. It moves the system from static to self-maintaining.

done when: a maintenance pass runs on its own and proposes real changes.
phase 03

Close the first gap

Before anything new joins the system, it passes a written policy and an admission checklist: scan it, read it for injection, sign off. Manual at first. It closes the gap that matters most, and you can automate it later.

done when: nothing enters the system without passing the gate.
phase 04

Make "good" a number

Put evaluations on your most-used assets so a new version has to earn its place instead of being trusted on sight.

done when: a version ships only after it beats the one it replaces.
phase 05

Close the loop

Capture what each run learned as something the maintenance agent reads on the next one. At this point the system stops being a thing you maintain and starts being a thing that maintains itself.

done when: outcomes from one run measurably improve the next.
05 · the through-line

From a setup you configure to a system you cultivate.

The five things a person sets up by hand become versioned nodes in a memory graph. Agents maintain them, evaluation grades them, and policy decides what's allowed. The operator's job moves up a level: from building the workspace to defining the taste and the rules that let the workspace build and improve itself. That is also the move from using these tools to designing the system other people work inside.
