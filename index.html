Substrate · a reference architecture

An agentic operating system for design organizations.

Design teams don't just need more tools. They need a system that remembers what they learn, gets better as they work, and looks after its own moving parts, so the people are free to set direction and taste.

01The shift

Designers stop being the hands for the machine.

A growing share of the work around AI tools is upkeep: writing context files, curating prompts, wiring things together, remembering which version is the good one. It's easy to underestimate, and it lands on the people you least want spending their time on it.

That shape works when one person is willing to keep it all up by hand. Substrate is the same shape made into the whole organization's system, kept current on its own. Here is what changes.

01 / memory

Knowledge stops evaporating.

What a project figures out goes into the organization's memory instead of disappearing when the session ends. The next person who picks it up, or the next agent, starts from what the last one learned.

02 / teams

The org chart includes agents.

Teams form around the work instead of being assembled by hand. A request finds the right specialists, and those specialists hand off to each other.

03 / capability

Each task gets only what it needs.

You describe what you're trying to do, and the system pulls together just the context, skills, agents, and tools that task needs, then puts them away when it's done. Nobody has to wire it up by hand first.

02The model · five layers, two planes

Everything is built around a shared memory at the center. Five layers sit on top of it, from that memory up to where the work actually runs, and two planes apply to all of them. Scroll to take them one at a time.

L0 · the core

Memory graph

the shared store everything else reads from and writes to

It holds every part of the system (the context, the skills, the agents, the tools) and the links between them, along with where each piece came from and how current it is. Everything above this layer is just a way of reading, changing, or adding to it. Because it is one connected store instead of scattered files, the system can see itself: what depends on what, and what has gone out of date.

L1 · the nodes

Asset plane

the things the system is made of, each one tracked like a file in version control

Five kinds of thing live here: context (what's true about your work), skills (how to do a task), agents (who does it), playbooks (how a job runs from start to finish), and tools (what those agents are allowed to touch). In most setups these are loose config you write once and forget. Here each one is a tracked, named item you can update, roll back, and reuse, so the rest of the system has solid pieces to work with.

L2 · identity

Registry & identity

the labels that say what each thing is, who made it, and whether to trust it

Every asset gets a name, a version, an owner, and a signature. That is the difference between a skill someone pasted in from somewhere and a skill you can actually check before you rely on it. It is how the system, and the people in it, tell a current, trusted asset from an old or unknown one.

L3 · the mediating agents

Control plane

the agents that do the setup and upkeep people used to do by hand

When you ask for something, these agents find the right context, skills, and tools, put together a team to do the work, and clear it away afterward. Others run quietly in the background, noticing when something has fallen out of date and proposing a fix. This is the layer that turns a pile of assets into a system that runs and looks after itself.

L4 · where work runs

Execution

where the actual work happens, and where the system learns from it

This is the part you would recognize: an agent or a person doing the task. What is different is what happens afterward. Every run reports back what it used, what worked, and what did not, and that record goes into memory. The next time similar work comes up, the system starts from what the last run learned instead of from scratch.

cross-cutting plane

Governance

the rules about what's allowed, enforced by the system instead of remembered by a person

Nothing joins the system without passing a check, and each asset carries its own limits: what it can touch, how sensitive it is. So the rules apply everywhere instead of living in one person's head. It sits across every layer because today's tools tell you who published something, not whether it is safe to run. This is the guardrail that makes the rest safe to automate.

cross-cutting plane

Evaluation

a way to measure whether a change actually made things better

Every asset carries a simple test for what 'good' means for it. When a new version of a skill or a playbook shows up, it has to beat the one it is replacing on that test before it goes live. This is what keeps the system improving on purpose instead of drifting, and it is why a version number here actually means something.

03Where to spend your effort

Buy. Assemble. Build.

Over the past year, the ways these tools connect to each other got standardized, and most of that plumbing is now settled. What didn't get settled is the part that matters most: trust, memory, and the loop that makes the system better over time. the map

Three kinds of layer

Five layers and two planes. Each one is either something you adopt as it is, something you wire together from emerging parts, or something you build yourself. Keep scrolling and the stack sorts itself into those three.

tier 01 · buy

Adopt what exists

The runtimes that actually run agents (Anthropic's Claude Agent SDK, LangGraph, OpenAI's Agents SDK) and the format skills are written in (the open SKILL.md standard, plus Claude Code plugins) are mature and widely supported. Use them as they are and spend your effort elsewhere.

tier 02 · assemble

Wire together what's emerging

The standards exist, but only in pieces. MCP connects agents to tools, A2A is the emerging one for agents talking to each other, and the MCP registry gives a tool a name and an address. They're real and still young, so you connect the registry and the control plane yourself, with a tool router like Composio or Zapier's MCP doing some of the wiring.

tier 03 · build

Own the core

The two parts with no ready-made answer. For memory, products like mem0, Zep, and Letta exist but none agree on a format, so you build a thin layer of your own over them. For governance, gateways like Cloudflare's MCP Portals and scanners like Snyk's MCP-Scan help, but the policy itself is yours. This is the part worth building, because it's where most of the system's value sits.

gap 01 · governance

Trust and safety review

Today's directories tell you who published something, not whether it's safe to run. People are already taking advantage of that: fake look-alike skills, tools with hidden instructions, real cases of credentials being stolen. Scanners like Snyk's MCP-Scan and signing tools like ToolHive help, but you still have to check everything before you let it in.

gap 02 · registry & identity

Versioning and signing for skills

Proper version control only exists inside Anthropic's API, and almost nowhere else. There's no standard way to lock a version or to prove a skill hasn't been tampered with; the usual signing tools haven't reached skills yet. So you set the habits yourself: track versions, keep a record of changes, and only promote a new one once it has been tested.

gap 03 · memory graph

Memory that interoperates

Good memory products exist (mem0, Zep, Letta, Cognee), but they all work differently and none of them agree on a common format. Build against a thin layer you control rather than committing to any one of them, so you can switch later without taking the system apart.

gap 04 · control plane

A trusted directory of agents

You can find an individual agent through its A2A 'agent card' if you know where to look, but there's no trusted, vetted directory of them yet, the way the MCP registry is starting to be for tools. For a small team this is something to plan for later, not a problem now.

gap 05 · evaluation

Evaluation across the system

You can test a single skill, tool, or memory store on its own. Benchmarks like BFCL and MCP-Bench, tools like LangSmith and Braintrust, and Anthropic's own skill benchmarks all do this. Testing the whole thing working together, end to end, is still unsolved. For now, test each piece on its own and keep a person reviewing where they connect.

04Building it · phase by phase

You don't build all of this at once to get value from it. You build the core and rough in the rest. Each phase is useful on its own and sets up the next. Scroll to walk through them.

  1. 00 set up the memory
  2. 01 put assets under version control
  3. 02 build the control plane
  4. 03 add the safety gate
  5. 04 prove new versions are better
  6. 05 let it improve itself
phase 00

Set up the memory

Pick one place to keep everything, and put a thin layer in front of it that the rest of the system talks to. Which store you pick matters less than that layer, because it's what lets you change your mind later.

done when: everything can be looked up from one place, and you could swap the storage underneath without redoing the work.
phase 01

Put assets under version control

Put your skills and plugins in one shared, version-controlled place, each with a version, an owner, and a simple index so things can be found. It's basic, but it works, and it's close to how this stuff already gets shared today.

done when: anything in the system can be found, has a version, and traces back to an owner.
phase 02

Build the control plane

One agent that takes a request and routes it to the right people and tools, and one that runs on a schedule, notices what has fallen out of date, and suggests fixes. This is the piece most worth building yourself, because it's what turns a fixed setup into one that keeps itself current.

done when: a maintenance run happens on its own and suggests real changes.
phase 03

Add the safety gate

Before anything new is allowed in, it goes through a short checklist: scan it, read it for hidden instructions, sign off. Do it by hand at first. It closes the most important gap, and you can automate the checklist later.

done when: nothing gets in without passing the check.
phase 04

Prove a new version is better

Put a simple test on the skills you use most, so a new version has to prove it's better before it replaces the old one.

done when: a new version goes live only after it beats the one it replaces.
phase 05

Let it improve itself

Save what each run learned in a form the maintenance agent reads before the next one. At this point you stop maintaining the system by hand, and it starts maintaining itself.

done when: what happens in one run measurably improves the next.
05 · the through-line

From a setup you configure to a system you cultivate.

The five things a person used to set up by hand now live in one shared memory. Agents keep them current, tests decide when a change is actually an improvement, and policy decides what's allowed. The person's job moves up a level: from building the setup to setting the taste and the rules that let the setup build and improve itself. That is also the move from using these tools to designing the system other people work inside.
